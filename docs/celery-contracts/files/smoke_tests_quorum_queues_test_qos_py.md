### `t/smoke/tests/quorum_queues/test_qos.py`

Portable guarantee: with late acknowledgement, one job in flight per worker slot, and a broker/database that drops out and returns, the worker must keep full capacity and keep consuming. Celery-specific parts (quorum queue per-consumer QoS, basic.qos) map to "claim limit / prefetch" in sqlery.

**Basic execution under late-ack, low-prefetch settings**
- Enqueue 1 job (add 1+2), run the worker; expect: job done, result 3.
- Enqueue 5 jobs (add i+i), run the worker; expect: all 5 done, each result is i*2, none lost or mixed up.

**Claim limit must not shrink after a connection loss**
- Worker with 4 slots, claim limit 1 per slot, late ack, claim-limit reduction enabled. Enqueue 4 long-running jobs; wait until all 4 are actually running (counted barrier, not just first one), then drop the database/broker connection and restart it; expect: log says reduction was skipped after reconnect, and the "temporarily reducing claim limit" message never appears.
- Reason: reducing the limit and restoring it per ack is a no-op when limits are per consumer, so the worker would stay stuck at reduced capacity forever; the reconnected worker must start at full claim limit.

**Worker resumes after reconnect (liveness)**
- Worker healthy first: enqueue a no-op job; expect: done, returns None.
- Enqueue 2 long-running late-ack jobs, wait until both are running, restart the broker/database; with cancel-on-connection-loss enabled, expect in-flight jobs are terminated and their slots freed, unacked jobs are redelivered.
- Then enqueue another no-op job; expect: it completes within the timeout (no deadlock from original plus redelivered copies filling all slots).
- Edge case: without cancel-on-connection-loss, original and redelivered copies would occupy every slot and starve new work; the guarantee is that slots are released on connection loss.
- Note: this test alone cannot distinguish the regression; the skip-log test above is the discriminating assertion.

**Test-design edge cases worth keeping**
- Waiting for N jobs to be in flight must count occurrences, not just detect the first, so the disconnect truly hits N busy slots.
- "Message never appears" checks must poll a window, not read a stale snapshot.
- Multi-worker race on claim limits could not be reproduced here (single worker only); sqlery should cover it with several workers claiming concurrently.
