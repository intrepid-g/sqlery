### Blockers/Concerns

- MIGRATION RENUMBER DECISION (2026-06-11): The ingest's "0029=cutover / 0030=staging" labels were renumbered to match execution order. Phase 14 staging = `0029_scheduled_job_staging` (depends on 0028). Phase 15 cutover = `0030_partition_queued_job` (depends on 0029). Chain: 0028 → 0029(staging) → 0030(cutover). All references to "migration 0029 (cutover)" / "migration 0030 (staging)" in older docs now mean the SWAPPED numbers.
- Phase 15 (schema-cutover) is the HIGHEST-RISK phase; its verification gates Phases 16–18. The cutover migration (now `0030_partition_queued_job`) is stop-the-world with a rename-based rollback — the ≥1M-row round-trip test is mandatory before proceeding.
- Index DDL byte-identity invariant: the 0028 partial index and the cutover-migration DDL (now 0030) must stay identical (`queue_name, priority DESC, created_at WHERE status='queued'`) or Phase 15 fails on a name collision.
- SHARED-ID-SEQUENCE DECISION (2026-06-11, Phase 15): Django GENERATED-AS-IDENTITY columns cannot be shared/re-owned, and the cutover re-forks the sequence — incompatible with the locked "shared id sequence" requirement. RESOLUTION (user-approved): use ONE standalone sequence `sqlery_job_id_seq`. Migration 0029 creates it, DROPs IDENTITY on both sqlery_queued_job.id and sqlery_scheduled_job.id, sets both defaults to `nextval('sqlery_job_id_seq')`, and seeds it past max(queued.id). Migration 0030 cutover keeps the new partitioned table's id defaulting to `nextval('sqlery_job_id_seq')` (NOT `ADD GENERATED BY DEFAULT AS IDENTITY` — that locked CONTEXT detail is superseded because it is the source of the conflict). This gives one monotonic id space across both tables that survives the cutover. SQLite path unaffected (vendor-guarded no-ops).
- PHASE 16 CARRY-FORWARD — RESOLVED (Phase 16): (1) `backend.get_raw_cursor()` wired (returns Django connection cursor on partitioned PG, None otherwise; daemon null-checks and skips PG-only maintenance/promotion cleanly). (2) SQLite far-future staging RESOLVED — `create_job` staging routing now gated on `_partitioned_pg()`, so SQLite/non-partitioned PG keep far-future jobs in `sqlery_queued_job` (D6); staging/promotion is partitioned-PG only.
