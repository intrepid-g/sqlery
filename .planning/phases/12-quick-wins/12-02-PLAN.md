<objective>
Replace the unbounded `.delete()` call in `cleanup_jobs` in both backends with a keyset-batched
loop (BATCH=500, `order_by("id")`, status re-check inside the DELETE, 0.1 s inter-batch sleep).

Purpose: Under a 100k-row backlog, the current implementation issues a single `DELETE` that holds
a table lock for multiple seconds, starving autovacuum and the claim path. The batched loop caps
lock-hold time per iteration, yields to autovacuum between batches, and never deletes a row that
was claimed while the loop was running.

This is the permanent path for SQLite and non-partitioned PostgreSQL (D6). The SQLite path is
unchanged in behavior — it uses this same batched loop with no partition emulation added.

Output: Updated `cleanup_jobs` in both backends + a new test file proving the key invariants.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Cleanup loop → database | Each batch issues a DELETE with status re-check; if a job was claimed between SELECT and DELETE, the re-check predicate saves it |
| Caller → cleanup_jobs | Status and queue_name parameters are user-supplied filter inputs that are passed to ORM `.filter()` — parameterized queries, no raw SQL injection risk |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-02-01 | Tampering | `cleanup_jobs` batch DELETE — race between SELECT ids and DELETE (mid-loop claim) | mitigate | Status re-check `status__in=FINISHED_STATUSES` inside the batch DELETE prevents deleting a row that transitioned to queued/running between the SELECT and DELETE |
| T-12-02-02 | Denial of Service | Inter-batch `time.sleep(0.1)` — cleanup takes longer under large backlogs | accept | Intentional: throttle prevents sustained dead-tuple burst; operational tradeoff documented in PLAN.md Step 2 |
| T-12-02-03 | Information Disclosure | `status` and `queue_name` filter params passed to ORM queries | accept | Django ORM and SQLAlchemy parameterize all filter values; no raw SQL |
| T-12-02-SC | Tampering | pip/cargo installs (slopcheck) | accept | No new dependencies introduced in this plan |
