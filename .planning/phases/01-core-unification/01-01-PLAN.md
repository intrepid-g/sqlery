<objective>
Make every module under `src/sqlery/core/` importable in a virtualenv without Django on `sys.path`. Today, `core/db_resilience.py` imports `django.db` unconditionally at module level, which breaks `import sqlery.core` in standalone mode and is the root cause of Phase 1 success criteria #1 failing. This plan guards every unguarded Django import in `core/` and adds standalone-equivalent behavior where the function is called outside Django mode.

Purpose: Satisfy UNIF-03/04/05/06 — `core/` is single-source-of-truth, callable from both backends.
Output: Five edited files, all unguarded `django.*` imports in `core/` either guarded with try/except, deferred into functions, or routed through `compat.get_backend()` / `get_config()`.
</objective>

When in standalone mode, call `get_backend().reset_connections()` if that method exists; otherwise no-op with a debug log. Use a function-local import `from sqlery.compat import get_backend, is_django_mode` to avoid circular issues at module load.
    6. In `configure_connection_resilience()`, replace `connection.vendor` lookup: use the guarded `_django_connection` when `is_django_mode()` is true; in standalone mode, obtain vendor from `get_backend().vendor` (assume the property exists on `DatabaseBackend`; if it does not, add it to the ABC and both implementations in a follow-up task — see Task 2). Replace the `try: from sqlery.django_sqlery.settings import get_setting except ImportError: get_setting = None` block: instead route through `from sqlery.compat import get_config` (function-local) and call `get_config().get_setting(name, default)`. Leave the `get_setting is None` fallback path for the truly-no-config case.
    8. Keep all behavior identical in Django mode — verify by running the existing test suite. Do NOT change `_configure_sqlite` / `_configure_postgresql` signatures; they still receive a `connection` object (cursor-bearing) and a settings callable.
