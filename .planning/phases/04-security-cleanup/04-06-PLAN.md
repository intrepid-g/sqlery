  <action>
    Create `docs/SECURITY.md` with the following sections (in order):

    1. **Overview** — one paragraph: Sqlery's threat model assumes the worker process is trusted; the dashboard, webhooks, and task imports are the operator-controlled attack surface. This doc covers how to harden each.

    2. **Dashboard Authentication (SEC-01)**
       - Three modes: `standalone` (default), `disabled`, `inherit`.
       - Env var: `SQLERY_DASHBOARD_AUTH` accepted values + precedence (explicit env > auto-detect).
       - Key resolution order: `SQLERY_DASHBOARD_API_KEY` env → `./.sqlery/dashboard.key` file → auto-generated 32-byte URL-safe token (logged once to stderr at startup).
       - File permissions: dir `0o700`, file `0o600`.
       - Auth header: `X-Sqlery-Key: <value>`.
       - Bypass: `GET /healthz` is unauthenticated in all modes for load balancers / orchestrators.
       - Mount detection: when Sqlery's FastAPI app is mounted as a sub-app of a parent ASGI app, Sqlery auto-detects and skips its own auth (trusts the parent's). Explicit env value overrides.
       - One worked example each for: production with rotating key, disabled for local dev, embedded in a parent FastAPI app.

    3. **Webhook SSRF Protection (SEC-02)**
       - Blocked ranges (full list from `src/sqlery/security/ssrf.py`).
       - How it works: `socket.getaddrinfo` resolve, check ALL returned IPs.
       - **Known limitation:** ~50ms DNS-rebinding window between validate and connect. v1 does not pin the resolved IP at the urllib3 level (deferred to v2).
       - How to override for legitimate private-network webhooks: call `validate_webhook_url(url, allow_loopback=True)` at the callsite OR patch `sqlery.security.ssrf.BLOCKED_V4_NETS` in your own settings module. There is intentionally NO project-wide allowlist knob to avoid footguns.

    4. **`ALLOWED_TASK_MODULES` (SEC-04)**
       - Default: unset = allow all (BC).
       - Set via Django `DJANGO_SQL_JOBS["ALLOWED_TASK_MODULES"]` (list[str]) or standalone `SQLERY_ALLOWED_TASK_MODULES` env var (comma-separated).
       - Prefix-with-dot-boundary semantics: `["myapp"]` matches `myapp.tasks` but NOT `myapp_evil.tasks`.
       - Production-env warning: when unset AND `ENV=*prod*` / `ENVIRONMENT=*prod*` / `DJANGO_SETTINGS_MODULE=*prod*`, worker startup emits one WARNING. To silence: set the option.

    5. **Django Admin CSRF (SEC-03)**
       - Default Django CSRF middleware applies to all admin endpoints.
       - Phase 04 audit found 11 state-changing endpoints in `api_views.py` previously bypassed via `@csrf_exempt` — these now require `X-CSRFToken` like any other Django admin POST.
       - The 3 remaining `@csrf_exempt` decorators in `views.py` are intentional and use token-auth instead of cookie-auth:
         - `internal_worker` — HMAC via `X-Signature` + `X-Timestamp` (5s expiry).
         - `health_check` — read-only liveness, no auth needed.
         - `trigger_view` — envelope HMAC via `core.triggers.handle` (SMOD-03 / DMOD-03).

    6. **Dead-code retention policy (CLEAN-01..04)**
       - Sqlery uses a mark-and-date pattern instead of immediate deletion: backward-compat shims and superseded modules carry `#CLEANUP YYYY-MM-DD ... Remove after YYYY-MM-DD` markers.
       - Default retention: 12 months from the mark date.
       - Deletion is a separate quarterly decision per-file once the `Remove after` date arrives.
       - Rationale: protects external consumers of legacy import paths and gives operators time to migrate.

    7. **Reporting security issues** — placeholder section if README doesn't already have a security contact: "Please report security issues privately by opening a [security advisory](https://github.com/...) or emailing the maintainer."

    Use concrete code blocks for env var examples. Use absolute file paths (`src/sqlery/...`) for code references. No marketing prose — operator-grade reference doc.
