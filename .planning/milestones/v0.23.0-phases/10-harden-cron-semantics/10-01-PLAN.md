<objective>
Add a single atomic primitive that folds CRON-01 (atomic enqueue + next_run_at advance) and CRON-04 (idempotency under two-leader overlap) into one mechanism: `advance_scheduled_task_if_due`. It conditionally advances a ScheduledTask's `next_run_at` ONLY when the row still equals the observed due time (a CAS on `next_run_at` — the ScheduledTask models have NO version column, confirmed by the pattern map, so the observed `next_run_at` is the idempotency token), and in the SAME transaction creates the queued job. Only the caller whose advance wins (rowcount == 1) enqueues, making double-fire impossible even if two leaders briefly overlap.

Purpose: The current scheduler does check-then-act (`has_pending_job_for_scheduled_task` -> `create_job` -> separate `update_scheduled_task_next_run`), which is two non-atomic ops AND a TOCTOU race. This plan replaces the reliance on that race with a single atomic txn at the backend layer. The scheduler is rewired to call it in Plan 03.

Output: One new ABC abstractmethod and two backend implementations with matching semantics across {Django, standalone} × {SQLite, Postgres}.
</objective>

## Trust Boundaries

| Boundary | Description |

| scheduler-leader -> ScheduledTask row | Two briefly-overlapping leaders cross here concurrently; the row is the contention point |
| backend -> database | All writes must be parameterized ORM; no string-built SQL |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-01 | Tampering/Race (TOCTOU) | advance_scheduled_task_if_due CAS on next_run_at | mitigate | Atomic conditional advance: Postgres `with_for_update()` blocking lock + read-compare-write; SQLite/Django `.update()` filtered on `next_run_at == observed` with rowcount==1. The advance IS the idempotency token — only one caller mutates the row, so double-fire is impossible even under two-leader overlap (closes Phase 9 WR-02). |
| T-10-02 | Denial of Service / skipped tick | crash between advance and enqueue | accept | Design is advance-wins-then-enqueue inside ONE transaction (SQLite predicate-CAS commits both; Django wraps both in transaction.atomic). A crash mid-transaction rolls back BOTH advance and enqueue, so the tick is neither skipped nor double-fired — it is retried next cycle. (If a future refactor split them, the documented tradeoff is: advance-then-crash skips one tick rather than double-firing — acceptable, but this plan avoids it via single-txn.) |
| T-10-03 | Information disclosure / Injection | SQL for the advance | mitigate | Parameterized ORM only (SQLModel `update()`/`select()`, Django queryset `.update()`/`.filter()`). No f-string or `.format()` SQL. |
| T-10-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages introduced (CLAUDE.md "no new dependencies"); all imports are already-declared deps. No install task in this plan, so no slopcheck/human checkpoint required. |
