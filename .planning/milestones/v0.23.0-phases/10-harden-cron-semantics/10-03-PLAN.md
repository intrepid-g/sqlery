<objective>
Rework `src/sqlery/core/scheduler.py` to consume the Plan 01 atomic primitive and the Plan 02 config key, delivering all four CRON requirements at the firing path that both the daemon (`daemon.py:433`) and the worker (`worker.py`, Phase 9) already share:

- **CRON-01 + CRON-04:** Replace the check-then-act sequence in `_enqueue_for_scheduled_task` (`has_pending_job_for_scheduled_task` -> `create_job` -> separate `update_scheduled_task_next_run`) with a SINGLE call to `backend.advance_scheduled_task_if_due(...)`. The atomic conditional advance IS the idempotency token: only the leader whose advance wins enqueues, so double-fire is impossible even under brief two-leader overlap (closes Phase 9 WR-02 and the WR-01 lease-renew overlap residual).
- **CRON-02:** Compute the next cron occurrence from `task.next_run_at` (the scheduled time), not wall-clock `now`, by passing `base_time=task.next_run_at` to `calculate_next_run`. When far behind, advance to the next FUTURE occurrence (clamp/loop) instead of replaying every missed tick.
- **CRON-03:** Read `get_config('scheduler_jitter_seconds', 0)`; when `> 0`, apply a bounded `random.uniform(0, jitter)` delay BEFORE enqueue, never feeding it into the next_run_at computation.

Purpose: This is where the phase goal becomes observable — cron fires exactly once, on schedule, with optional spread, across crashes and overlap.

Output: A hardened `_enqueue_for_scheduled_task` + `calculate_next_run` (cron path) + jitter application, preserving the interval/once branches and the per-task resilient loop.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| two overlapping scheduler-leaders -> same ScheduledTask | Both may read the same observed_due and attempt to fire; the CAS at the backend is the single arbiter |
| operator config -> enqueue timing | scheduler_jitter_seconds delays enqueue; must be bounded and config-only |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-05 | Tampering/Race (double-fire under overlap) | _enqueue_for_scheduled_task cron path | mitigate | Replace check-then-act with the single atomic advance_scheduled_task_if_due call; only the CAS winner enqueues. Correctness no longer depends on perfect single-leadership (closes Phase 9 WR-02 and the WR-01 in-wait lease-renew overlap residual — the wider overlap window cannot cause double-fire because the advance is the idempotency token). |
| T-10-06 | DoS (skipped tick on crash) | advance-then-enqueue ordering | accept | Advance and enqueue are atomic in one backend txn (Plan 01); a crash rolls both back, so the tick is retried next cycle, not skipped or doubled. Jitter sleep happens BEFORE the atomic advance, so a crash during the sleep simply means the tick is re-evaluated next cycle — no partial state. |
| T-10-07 | DoS (covert delay channel via jitter) | scheduler_jitter_seconds | mitigate | Delay is config-only (operator-set, default 0, not request-derived) and bounded to random.uniform(0, jitter). It is applied to enqueue timing only and never feeds calculate_next_run, so it cannot corrupt drift/idempotency correctness. |
| T-10-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages; random/time are stdlib. No install task, so no slopcheck/human checkpoint required. |
</threat_model>
