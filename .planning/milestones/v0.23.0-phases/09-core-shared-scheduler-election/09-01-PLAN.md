<objective>
Wire the daemon's per-queue scheduler-election lifecycle into the worker poll loop so a bare `sqlery-worker` self-elects as scheduler-leader. Each poll cycle the worker claims/renews the `sqlery_daemon_lease` for every queue in `self.queues` using its own identity, runs `scheduler.run_due_tasks` only for queues it holds, and releases held leases on graceful shutdown. A live daemon keeps winning its leases (enforced by the lease primitive), so the daemon stays authoritative.

Purpose: In bare-worker deployments (no daemon) nobody fires recurring cron `ScheduledTask`s today. This makes a plain worker watch the clock for the queues it leads, at parity across Django and standalone.

Output: Election lifecycle inside `WorkerProcess.run` in `src/sqlery/core/worker.py` (claim before loop, renew + re-claim-expired + fire-cron per cycle, release in `finally`). No backend, model, config, or scheduler changes — Phase 8 already supplies the lease methods in both modes.

Scope boundary: This plan wires election + cron-firing ONLY. It does NOT touch the job-claim path (`backend.claim_job(self.queues, ...)` at worker.py:505 stays exactly as-is — ELECT-07), and it does NOT implement cron-semantics hardening (atomic enqueue+advance, drift, jitter, idempotency under overlap — Phase 10) or parity CI tests (Phase 11). Tests for this wiring live in Plan 02.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| worker process → DB (lease rows) | The worker writes/reads `sqlery_daemon_lease` rows. Lease identity (`worker_id`, `node_id`, `pid`) is process-derived, not user input. |
| concurrent leaders → shared cron state | Two processes (daemon + worker, or two workers) may briefly both believe they hold a queue lease during a TTL boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-09-01 | Elevation of Privilege | worker stealing a daemon's live lease | mitigate | Reuse the existing per-queue lease primitive whose claim path skips live foreign leases (compat/__init__.py:128-129); the worker never special-cases or steals — daemon stays authoritative (ELECT-05). No new probe. |
| T-09-02 | Denial of Service | a crashed leader holding a lease until TTL expiry | accept | TTL = `poll_interval * 3` (≈30s) self-heals: the next cycle's re-claim of `unowned` takes over the expired lease (ELECT-06). Acceptable scheduling gap; cron is recurring, not real-time. |
| T-09-03 | Tampering (double-fire) | brief two-leader overlap firing the same cron tick twice | accept (deferred to Phase 10) | Out of scope here. The "already queued" idempotency guard hardening that makes a tick fire exactly-once under overlap is CRON-04 / Phase 10. This plan notes the risk and does not solve it. |
| T-09-04 | Denial of Service | an election exception (claim/renew/run_due_tasks/release) crashing the worker | mitigate | Every election call is wrapped in try/except-log-and-continue (worker.py:562-567 convention); a failed election degrades to "this worker doesn't schedule this cycle" but it still claims and executes jobs (ELECT-07 safe-degradation). |
| T-09-SC | Tampering | npm/pip/cargo installs | n/a | No package installs in this phase — no new dependencies (CLAUDE.md constraint; reuses Phase 8 lease methods and existing `Scheduler`). No legitimacy checkpoint required. |
</threat_model>
